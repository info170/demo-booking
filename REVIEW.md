## Code review

### Обнаруженные проблемы

### 1. Critical:

#### 1.1 Секреты и пароль БД прописаны в compose-файле

`compose.yaml`

<u>Как исправить:</u> для паролей использовать переменные окружения, разные сильные пароли и не публиковать порт PostgreSQL в production.

#### 1.2 Возможны SQL-инъекции в проверке пересечений

`BookingController::store`

Значения из запроса вставляются в SQL через интерполяцию. Злоумышленник может изменить запрос или получить ошибку с раскрытием внутренней информации.

<u>Как исправить:</u> добавить строгую валидацию типов и дат, использовать Eloquent/query builder или параметры запроса.

### 2. Major:

#### 2.1 Можно создавать бронирование от имени другого пользователя

`BookingController::store`

`Booking::create($request->all())` принимает `user_id` из тела запроса, а атрибут разрешён в `fillable`.

<u>Как исправить:</u> не принимать `user_id` от клиента; присваивать его из `$request->user()->id`. Создавать запись только из validated-данных.

#### 2.2 Нет проверки прав при удалении

`BookingController::destroy`.

Любой авторизованный пользователь может удалить бронирование, зная его ID.

<u>Как исправить:</u> например можно использовать route model binding и policy: `$this->authorize('delete', $booking)`.

#### 2.3 Нет входной валидации

`BookingController::store`.

Не проверяются существование комнаты, обязательность и формат полей, `ends_at > starts_at`, длительность и полный рабочий интервал.

<u>Как исправить:</u> добавить Form Request с правилами `required`, `exists:rooms,id`, `date`, `after:starts_at`, `string|max:...` и отдельной проверкой интервала.

#### 2.4 Гонка данных при проверке пересечений

`BookingController::store`

Два параллельных запроса могут одновременно пройти SELECT-проверку и создать пересекающиеся бронирования.

<u>Как исправить:</u> добавить транзакцию с блокировкой и ограничение PostgreSQL (exclusion constraint по комнате и диапазону времени).

### 3. Minor:

#### 3.1 Проверяется только час начала

Проверка `start->hour` разрешает интервал вроде 19:30–21:00 и не учитывает минуты.

<u>Как исправить:</u> проверять начало не раньше 09:00 и конец не позже 20:00 с учётом часового пояса выбранного офиса.

#### 3.2 Часовой пояс выбран неявно

`today()` и проверка рабочих часов используют часовой пояс приложения, хотя у офиса есть свой `timezone`.

<u>Как исправить:</u> явно преобразовывать даты в часовой пояс офиса перед фильтрацией и проверками.

#### 3.3 Правильная сортировка ответа

В `today()` порядок записей не гарантирован БД.

<u>Как исправить:</u> добавить необходимую сотртировку, например `orderBy('starts_at')`

#### 3.4 Неоптимизированный запрос N+1

`BookingController::today`

'author' => $b->user->name для каждой брони делает отдельный SELECT * FROM users

<u>Как исправить:</u> добавить with (жадную загрузку) `return $room->bookings()->with('user')`

#### 3.5 Желательно запросы без RAW

`BookingController::index`

В запросе orderByRaw('starts_at DESC')

<u>Как исправить:</u> заменить на orderByDesc('starts_at')

#### 3.6 Миграции без timezone

В миграциях используется timestamp('starts_at') и timestamp('ends_at')

<u>Как исправить:</u> использовать timestampTz либо явно нормализовать все даты в UTC

### Подозрительные места

- `127.0.0.1:5433:5432` — в production такой проброс нужно убрать, чтобы БД не была доступна снаружи.
- `auth:sanctum` проверяет, что запрос аутентифицирован (есть валидный токен). Но это не значит, что пользователь имеет право на определенные действия. Нужна ещё проверка владения (например, booking->user_id === auth()->id() или Policy)
